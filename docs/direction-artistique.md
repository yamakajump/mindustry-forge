# Art direction

What the brand is, which file answers which system, and what not to do with it.

None of this is a redesign. The site already had a sound palette and the game's own
typeface. What it did not have was a mark, a valid icon, or a thumbnail for a shared link.
That is the hole this fills.

## The mark

An **F built like a run of conveyor**. The stem is the intake, the top arm leaves through
a point. A Mindustry player reads the gesture before the letter, and a reader who does not
know the game still reads an F.

```
site/public/brand/mark-plain.svg     the geometry, drawn by hand. THE source.
site/public/brand/mark.svg           the mark on its plate, generous framing
site/public/brand/logo.svg           the full lock-up, two tones
site/public/brand/logo-mono.svg      the same, in currentColor
```

**`mark-plain.svg` is the only file in that list anyone edits.** Everything else, `mark.svg`
included, is regenerated by `tools/build_brand.py`, which reads its paths.

### The geometry is copied three times, and a test is what holds it

This page first **forbade** copying the paths anywhere. The prohibition was in the wrong
place, and the lane that put the mark in the headers went around it for a good reason: an
`<img>` does not let `currentColor` through, so a mark placed as an image would follow
neither the colour nor the size of its neighbour, which is exactly the property we were
after. It has to be inline SVG, so one copy per header.

There are **three**, not two as this page assumed:

```
site/resources/views/layout.blade.php        the pages Laravel renders
site/public/index.html                       the analyser, static
site/public/forge/editor/mount.js            the editor bar, written in JavaScript
```

The third is the one that gets forgotten, and it is **precisely the surface the `em` sizing
was designed for**: the editor bar redefines `.brand` at 17px. The justification existed;
the surface it protected was not being served.

`site/tests/Feature/NavigationTest.php` reads the four paths out of `brand/mark-plain.svg`
and compares them to the three copies. **A rule that forbids what you need gets worked
around; a rule that checks it holds.** The wording is the correcting lane's, and it is worth
more than this one case.

### The grid rule

The mark is drawn on a 32-unit grid, **and every one of its coordinates is even**. At 16
pixels two units are exactly one pixel: the stroke lands on the screen grid and does not
smear. An odd coordinate introduced into `mark-plain.svg` makes the favicon fuzzy at the
size where it is seen most, and that stays invisible for as long as you look at the SVG
large.

Stroke weight: 4 units throughout, stem and arms alike. The point overshoots the cap line by
2 units, and that is deliberate: without it the mark looks smaller than the text beside it.

### What not to do with it

- **Do not replace the `<header>` text with an image.** `.brand` is used in three places,
  and the editor bar redefines its size to 17px. The mark goes **inline**, in
  `currentColor`, with a height in `em`: it then follows the colour and the size of its
  neighbour with nobody having to maintain it.
- No rotation, no mirroring, no gradient inside the mark.
- No amber on a light ground without the plate: `#ffd37f` on white is a contrast ratio of
  roughly 1.5. That is what the dark plate is for, and why it is not decoration.
- Minimum clear space around the mark: the width of its own stem, 4 units of its own grid.

## The palette

It comes from the game and it does not change. A player recognises these colours before
reading the site's name.

| Token | Value | What it is |
|---|---|---|
| `--bg` | `#12161b` | the ground, and the mark's plate |
| `--panel` | `#1b2027` | the header and the cards |
| `--raised` | `#232932` | anything clickable |
| `--edge` | `#2f3742` | every border |
| `--ink` | `#e9edf3` | text |
| `--dim` | `#9aa4b2` | secondary text |
| `--accent` | `#ffd37f` | the brand, and one thing per screen |
| `--good` `--bad` `--warn` | `#84d98b` `#ff8b8b` `#ffbe6b` | states, never decoration |

### Thirteen colours that should have been tokens

`forge.css` opens on this sentence:

> *two copies of a palette is how a site comes to have two slightly different yellows*

And the file carried **13 hex literals repeated 22 times outside `:root`**. The most used,
`#e0b45f`, appeared four times. The file contradicted its own principle.

**Applied**, in `forge.css`, with the nineteen matching literals replaced:

```css
--accent-strong:  #e0b45f;   /* the border of a primary button   (4 occurrences) */
--accent-soft:    #ffdd9c;   /* that same button, hovered        (2 occurrences) */
--on-accent:      #241d0c;   /* text sitting on amber            (4 occurrences) */
--accent-pressed: #2f2a1c;   /* the fill of a pressed control    (3 occurrences) */
--raised-hover:   #2b323c;   /* something clickable, hovered                     */
--stage:          #0e1116;   /* the board the plan lives on      (2 occurrences) */
--bad-panel:      #2a1c1c;   /* the ground of an error message   (2 occurrences) */
--discord-hover:  #6a76f5;   /* the Discord button, hovered                      */
```

No new value. These are the colours already written out in the body of the file, named
where they should have been. What it buys is that adjusting the amber one day happens in
one place instead of fourteen.

**Measured twice, by two lanes, with two harnesses.** The whole transformation applied to
one checkout, before-and-after captures in the same session, full palettes compared rather
than pixels:

| Page | Palette before → after | Colours | Pixels |
|---|---|---|---|
| showcase | 2778 → 2778 | +0 / -0 | 0 |
| analyser | 1987 → 1987 | +0 / -0 | 0 |
| editor | 2544 → 2544 | +0 / -0 | 0 |

The palette diff is the right signal, and a better one than a pixel diff: **a hex value
copied wrong adds one colour and removes another** even when it tints three pixels in a
border, whereas a pixel count says something moved without saying which token is at fault.

Two things that went wrong while measuring, both worth knowing:

- The first pass of one harness reported "identical" while photographing **the Laravel
  exception page twice**, because a development database was missing migrations. A test
  that compares an error to the same error always passes. Both harnesses now assert the
  page title before measuring.
- Full-page capture has a noise floor of **one pixel** on the analysis report, always in the
  same place, an antialiased canvas edge. One pixel is not a colour change, and the palette
  measure ignores it.

`--accent-pressed` was first called `--accent-veil`, and that was wrong. Its three call
sites are all `[aria-pressed="true"]` paired with an `--accent` border: it is the fill of a
pressed control, not a low-opacity amber veil. **A token named after its appearance does not
tell the next lane whether it may use it; one named after its role does.**

### Four literals remain, and the last one is a real defect

Three stay on purpose: `#fff` in `a.discord` (pure white, naming it teaches nothing),
`#ffd37f0f` (that is `--accent` at 6 % opacity, not a colour of its own) and `#10140f` (text
on `--good`, one occurrence, a distinct role).

The fourth, `#1a1d23`, **is a visual defect and not a naming question**:

```
194  background: var(--accent); color: #241d0c;   primary button
452  background: var(--accent); color: #241d0c;
556  color: #241d0c; background: var(--accent);
609  color: #241d0c; background: var(--accent);
307  background: var(--accent); color: #1a1d23;   .manage .seg button.on
```

**Five places put text on the same amber. Four write `#241d0c`, the fifth `#1a1d23`.**
Measured rather than settled by counting occurrences:

```
#241d0c on #ffd37f    contrast 11.84:1    L* 11.1   a* +0.5   b* +11.6
#1a1d23 on #ffd37f    contrast 11.96:1    L* 10.7   a* +0.3   b*  -4.6
                                          deltaE76 = 16.2
```

The contrasts are a hundredth apart, so this is not legibility and neither value is the
safer one. But 16.2 of deltaE, when 5 is enough to see a difference clearly, and the gap is
almost entirely on the warm-cold axis: a brown ink and a blue-grey ink on the same yellow,
between two neighbouring buttons with the same function. That does not read as a choice.

`#241d0c` everywhere, **decided 27/08/2026**, carried separately by the lane that owns
`.manage .seg`. It changes what the site looks like, so it had no business travelling inside
a change whose whole argument is that it changes nothing.

## Type

`Forge` and `Forge Mono`, lifted out of the game's jar by `tools/build_fonts.py` and subset
to 10 and 37 kB.

**The face covers every French accent.** Checked glyph by glyph across the subset's 202
glyphs: `é è ê ë à â ç û ù ü ô ö î ï œ É È À Ç « » ° ²`, none missing. The site's
accent-free strings were a convention, not a technical constraint.

### The two faces are not under the same licence

`site/public/forge/fonts/README.md` holds the survey, done by reading each file's `name`
table rather than by assuming:

- **`forge.woff2`**, the one the identity is built on, rests on Anuke's position for the
  game's assets. **Nothing in the file confirms it.**
- **`forge-mono.woff2` is Fira Code Medium**, a third-party face under **SIL Open Font
  License 1.1** that Anuke redistributes without having written it. `build_fonts.py`'s
  reasoning did not cover it. `FiraCode-OFL.txt` sits next to it, which is what the OFL
  asks.

What that means for the brand: **the monogram depends on no typeface.** It is drawn in
paths, not set in letters, so a change of face does not touch it. What depends on
`forge.woff2` is the lock-up and the text of the shared images, and those recompose in one
run of `build_brand.py`.

`resources/fonts/forge.ttf` is a derivative of `forge.woff2` for the server, not a second
face: see `site/resources/fonts/README.md`.

**Still open, and not for a session to settle**: making a face lifted from a third-party
game into an element of brand identity is not quite the same use as displaying text with it,
and this repository is AGPL-3.0. If certainty is wanted, the licence of Mindustry's assets
is what has to be read at the source. Nothing is blocked today, and the fallback is one line
of CSS, since the mark itself does not move.

## The files, and what each one answers

| File | Size | Who asks for it |
|---|---|---|
| `favicon.ico` | 16 + 32 + 48 | whatever hits `/favicon.ico` without reading the `<head>` |
| `favicon.svg` | vector | any current browser |
| `apple-touch-icon.png` | 180 | the iOS home screen |
| `icon-192.png` `icon-512.png` | `purpose: any` | the manifest |
| `icon-maskable-512.png` | `purpose: maskable` | Android, which cuts its own shape out of it |
| `og.jpg` `og-schematiques.jpg` | 1200 × 630 | Discord, Twitter, anything that unfurls a link |
| `site.webmanifest` | n/a | installing on a phone |
| `brand/discord-icon.png` | 512 | the server icon |
| `brand/discord-banniere.jpg` | 960 × 540 | the server banner |
| `brand/apercu-produit.png` | 2144 × 1420 | the product shot, for a landing page or an article |

Three different framings of one mark, because the systems do not crop alike:

- **A browser tab** crops nothing, but the mark is only 8 pixels tall there. Tight framing,
  76 % of the width, no border: at that size a 2-unit border eats the contrast instead of
  giving the mark a body.
- **iOS** rounds the corners itself and ignores transparency. So square corners and a solid
  ground. An already-rounded icon comes out double-rounded with a black rim.
- **Android maskable** only guarantees the central 80 %. The mark drops to 46 % of the
  width, which leaves it whole even inside the tightest circle.

## Per-schematic share cards

`app/Services/SocialCard.php` composes them with GD, `SocialCardController` serves them at
`/s/{slug}/carte.jpg` and keeps them on disk.

The page used to push **the raw plan render** as `og:image`. A plan is square or very long
depending on what was copied, so an unfurler crops it or sits it on black bars, and it
carries no title, no figure and no mark. Worse, **a schematic with no preview pushed no
image at all**, which is the state of everything arriving from the two catalogues being
ingested.

On demand rather than at save time, for three reasons: the thousands of imported schematics
do not each have to produce an image nobody will ask for, rows already in the database
benefit without a replay, and changing the layout means emptying a directory rather than
writing a migration. A card is rebuilt when `updated_at` passes the file's date, because a
card that never regenerates ends up quoting a throughput the page no longer states.

The plan is scaled **nearest-neighbour and at an integer factor** while that is possible.
This is pixel art: bilinear smoothing turns a conveyor belt into a grey smear, and a
fractional factor gives one column in three a different width, which is glaring on a grid.

Two derived files come out of `build_brand.py` for it: `resources/brand/mark-96.png` (the
mark on transparency, which PHP pastes instead of redrawing its paths) and
`resources/fonts/forge.ttf` (the same face out of its WOFF2 wrapper, because FreeType does
not read WOFF2). Neither is a second source.

## Regenerating

```bash
python tools/build_brand.py
```

Rebuilds everything from `mark-plain.svg`, the typeface and `brand/fond-usine.png`. None of
the produced files is retouched by hand: a retouch would drift from its source at the next
run with nothing to say so.

**Two files are exceptions.**

`brand/apercu-produit.png` is a **real capture** of the site analysing a schematic, not an
illustration. The plan in it is built by a script that uses the same `.msch` writer as the
tests, and the figures shown are the ones the analysis computes. Drawing that visual would
have been quicker and would have produced an image announcing a result nobody measured, in a
repository whose second rule is that the figures have to be proven.

`brand/fond-usine.png` is the other one. It is a generative model's output, produced once and
committed as is. It is not regenerated per build: a model's output is not reproducible, and a
brand whose illustration changes every build is not a brand. It is committed **in
greyscale**, because `tritone()` starts with `convert("L")` and throws the colour away, so
keeping it cost 1.2 MB of information no code reads. It is then graded into the site's three
tones, because it came out navy and orange, and two yellows arguing are worth less than one.
